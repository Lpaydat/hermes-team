# Model Audit Technique — Find Stale Model References

**Added:** 2026-08-10
**Trigger:** User says "we still using model X somewhere" or "use only model Y for main task"

## The Audit

When the user asks to audit all model references across the system, search three layers:

### 1. Profile configs (config.yaml)

```bash
# Search all profile configs for model references
grep -rn 'glm-4\|deepseek\|model:' startup/profiles/*/config.yaml
```

Check for:
- `model.default` — the main model (should be the approved one)
- `auxiliary.vision.model` — vision model (easy to forget, often stale)
- `fallback_providers` — fallback models (acceptable as fallback-only, not main)
- `delegation.model` — model used for delegated subagents

### 2. Cron jobs (jobs.json)

```bash
# Cron jobs can pin models per-job
grep '"model"' startup/profiles/*/cron/jobs.json | grep -v null
```

Jobs with `"model": null` inherit the profile default (correct). Jobs with
a pinned model string override the default — check if the pin is stale.

Also check `cron/output/` for stale error messages referencing old models
(drift detection errors from `hermes` runtime).

### 3. Workflow templates (JSON)

```python
import json, os
TEMPLATE_DIR = "startup/scripts/workflow_engine/templates"
active = [f for f in os.listdir(TEMPLATE_DIR) if f.endswith('.json') and not f.endswith('.disabled')]
for f in active:
    d = json.load(open(os.path.join(TEMPLATE_DIR, f)))
    for n in d.get('nodes', []):
        body = n.get('body_template', '')
        for term in ['glm-4', 'deepseek', 'gpt-', 'claude-', 'model:']:
            if term in body.lower():
                print(f"{f}/{n['id']}: {term}")
```

Templates generally don't pin models (cards inherit profile defaults), but
check anyway — a stale template instruction could reference a specific model.

## What to Fix

- `auxiliary.vision.model`: update to the approved model (vision configs are
  frequently forgotten when the main model changes)
- Pinned cron jobs: update or unpin (`model: null`) to inherit default
- Template body references: remove model-specific mentions

## What's Acceptable

- `fallback_providers` with a different model: acceptable IF it only fires
  when the primary fails. Ask the user if unsure — they may want fallback
  removed entirely ("glm-5.2 only, no fallback") or kept as reliability.
- `model: null` in cron jobs: correct — inherits profile default.
- Stress test scripts that hardcode models as test parameters: these are
  test artifacts, not pipeline code. Leave them.

## Proven Case (2026-08-10)

User asked to find all glm-4.6/4.7 references. Audit found:
- Builder `auxiliary.vision.model: glm-4.6` — FIXED to glm-5.2 (commit f87c471)
- Builder cron jobs — stale error messages, actual pins are `model: null` (OK)
- Stress test scripts (round3/4) — hardcode glm-4.6 as test parameter (OK, test artifact)
- Product-owner `fallback_providers: deepseek-v4-flash` — kept as fallback-only (user approved)

## API-Side Model Name Bug (important diagnostic)

The ZAI Coding Plan API returns "glm-4.7" as the model name in API
responses **regardless of which model you actually requested**. This is
a known API-side behavior, documented in
`hermes-agent/agent/system_prompt.py:329`:

```python
# Alibaba Coding Plan API always returns "glm-4.7" as model name regardless
# of the requested model. Inject explicit model identity into the system prompt
# so the agent can correctly report which model it is.
```

**Implication:** If the user sees "glm-4.7" on their provider API dashboard
or in API response logs, it does NOT mean our config is calling glm-4.7.
Our configs are correct (all glm-5.2). The dashboard is showing the
API response model name, not the request model. Do not chase this as a
config bug — explain it as the known API-side behavior.

## Cache Files Are Harmless (don't chase)

Auto-generated cache files under `profiles/*/cache/` and `profiles/*/` root
contain glm-4 model names:

- `provider_models_cache.json` — lists ALL models available from the provider API
- `openrouter_model_metadata.json` — full OpenRouter model catalog
- `ollama_cloud_models_cache.json` — full Ollama Cloud model list

These are auto-generated by the provider API discovery, not config. They
will always list every model the provider offers, including old ones. They
regenerate automatically. Do NOT try to edit or suppress these — they are
read-only metadata caches.

## auxiliary_client.py Default Fallback (hermes-agent code, not ours)

`hermes-agent/agent/auxiliary_client.py:718` has a hardcoded fallback:

```python
_API_KEY_PROVIDER_AUX_MODELS_FALLBACK = {
    "zai": "glm-4.5-flash",
    ...
}
```

This fires ONLY when a profile has NO explicit `auxiliary` config. Since
all our profiles inherit the global default (which sets vision to
glm-5.2 on builder), this fallback should not fire. But if a new profile
is created without an auxiliary config, it would use glm-4.5-flash for
auxiliary/vision calls. This is hermes-agent code — report it upstream,
don't try to patch it locally.
