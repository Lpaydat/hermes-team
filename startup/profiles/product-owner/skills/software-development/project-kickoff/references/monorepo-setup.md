# Monorepo Setup for Full-Stack Projects

When a project has both a frontend and backend (or multiple deployable components), use a monorepo rather than separate repos. This keeps the domain model, ADRs, and project steering docs in one place and makes cross-cutting changes (schema updates that affect both frontend types and backend rules) atomic.

## Directory structure

```
<project-slug>/
├── frontend/          # PWA, SPA, or app shell (React/Vite, Next.js, etc.)
├── backend/           # Backend binary, server, or API (PocketBase, FastAPI, etc.)
├── scripts/           # Migration, deployment, and ops scripts
├── docs/              # ADRs, architecture diagrams
│   └── adr/
├── .driver/           # Project steering (PO-owned)
│   ├── goal.md
│   ├── spec.md
│   ├── design.md
│   └── planning/
├── .beads/            # Issue tracking (auto-generated by bd init)
├── AGENTS.md          # Agent instructions (auto-generated by bd init)
├── CLAUDE.md          # Claude Code integration (auto-generated by bd init)
├── README.md
└── .gitignore
```

## .gitignore patterns for a monorepo

The `.gitignore` needs to cover BOTH frontend and backend artifacts, plus agent-generated session data that should never be committed:

```gitignore
# Dependencies
node_modules/

# Build outputs
dist/
build/
.vite/

# Backend data (PocketBase / SQLite)
pb_data/
*.db
*.db-journal
*.db-wal
*.db-shm

# Environment
.env
.env.local
.env.*.local

# IDE
.idea/
.vscode/
*.swp

# OS
.DS_Store
Thumbs.db

# Logs
*.log

# PWA
dev-dist/

# Test coverage
coverage/

# Agent-generated worktrees (not source code)
.worktrees/

# Agent session data (not app source)
traces/
journal/
.pi/
.harness-prompt.md
```

## GitHub repo creation

```bash
gh repo create <owner>/<slug> --private --description "<description>" --clone=false
git remote add origin git@github.com:<owner>/<slug>.git
```

After the first push, set the default branch:

```bash
gh repo edit <owner>/<slug> --default-branch master
```

## Old repos as read-only reference

For migration projects, the old repos stay frozen. Never modify them directly. Reference them in the README:

```markdown
## Reference (old system, read-only)
- Frontend: https://github.com/<owner>/<old-frontend>
- Backend: https://github.com/<owner>/<old-backend>
```

The old repos are the source of truth for the migration script and the reference for old UI patterns. The new monorepo is a clean start — new stack, new architecture, new git history.

## Worktree management

When the builder dispatches tasks, worktrees are created under `.worktrees/`. These must be in `.gitignore` — they contain per-task agent session state, not app source code. The builder's code lands on feature branches in the main repo, not inside worktree directories.

If worktrees accumulate (abandoned tasks, retries), clean them up:

```bash
git worktree prune
rm -rf .worktrees/
```
