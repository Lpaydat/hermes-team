# task-system-boundary — beads is the spec, kanban is the engine

Two task systems run side by side. Knowing the boundary prevents misplacing state
and reasoning incorrectly about what survives when things go wrong. This skill is
architectural understanding, not command syntax — see the beads skill and
KANBAN_GUIDANCE for mechanics.

## The Boundary

```
Beads (bd / Dolt)     = Source of truth for WHAT and WHY
                        Durable, versioned, git-synced, recoverable from remote

Kanban (SQLite)       = Transient execution layer
                        Dispatch, claim, crash recovery, circuit breaker
                        Local-only — rebuildable from beads
```

The bead-sync phase (workflow engine, per board) syncs kanban status → bead status.
This direction makes beads the durable canonical store and kanban the ephemeral
engine. **If the kanban board is lost, it should be reconstructable from beads.**

**One-line test:** *Would a human want to see this in the backlog a month from now?* Yes → bead. No → card. See [`references/artifact-routing-policy.md`](references/artifact-routing-policy.md) for the full decision matrix.

### The engine's read/write contract

When the workflow engine (the bridge) is in play, the boundary is **asymmetric**:
the engine has **read-triggers + write-status-only** privilege on beads, and
**full read/write** privilege on kanban. The sole allowed bead write is
`bd update <id> -s <status>`; the engine never authors, links, or re-types bead
definitions (`bd create`, `bd dep add`, `bd tag` are all forbidden to the engine —
authorship is a profile/human privilege). Status sync is unidirectional
(kanban → beads), joined by the `bead-<id>` idempotency key. See
[`references/engine-read-write-contract.md`](references/engine-read-write-contract.md)
for the full contract (trigger families, status map, template-referencing model,
anti-patterns).

## Design Principles

1. **Task definitions originate in beads** — survives disk failure via git remote.
2. **Kanban cards reference their bead IDs** — so the board can be rebuilt.
3. **Never treat kanban as the sole store of a task's definition** — only its execution state.
4. **Bead-sync must run frequently enough** that the board is always reconstructable.

## When to Consult This Skill

- **"What happens if the board crashes?"** — see Failure/Recovery reference.
- **"Can two agents grab the same task?"** — yes, both have atomic claim; kanban's CAS is documented in the reference.
- **"Where should I store this state?"** — if it must survive hardware loss, it belongs in beads.
- **"Why did the dispatcher spawn / not spawn / re-spawn?"** — see the 7-layer double-dispatch prevention in the reference.
- **"Can we trace this bug back to the task?"** — beads has full Dolt version history; kanban has an append-only event log.

## Known Quirks

- **`bd create --type=bug` does not set `issue_type` to `bug` reliably.** It may set the title to "bug" but leave `issue_type` as `task`. If the workflow engine routes by `issue_type == "bug"`, the routing may not fire. Workaround: the PO's dispatch skill recognizes bug content and routes to debugger regardless of issue_type. The engine's `dispatch_bug_to_debugger()` also checks `issue_type == "bug"` — verify the bead has the correct type before relying on automatic routing.
- **`hermes kanban create` CLI does not accept `--skills`.** That's a `kanban_create` tool parameter, not a CLI flag. Passing it causes `unrecognized arguments` and the card creation fails silently in the workflow engine. Never pass `--skills` to `run_kanban()` calls.
- **Agent-creates-card is fragile for process-compliance steps.** The debugger's natural instinct is to diagnose and close — not to spawn QA re-test cards. When a handoff step is critical for pipeline correctness (like QA re-test after bug fix), move it to infrastructure (workflow engine hook) rather than relying on the agent reading its SOUL.md. The QA trigger was moved from verifier/debugger SOUL.md instructions to workflow engine phase 5 — a card-based scan that fires when any verifier/debugger card completes. Five iterations to get right: (1) git HEAD tracking (false positives on spec commits), (2) git-with-merge-count (first-run seeding bug), (3) card-based scan without debugger loop filter (spurious QA cards from loop_engine internal verifier cards), (4) parent-child debugger filter (missed loop_engine's complex parent chains), (5) regex merge detection on completion summaries (clean — fires on "merged to master", ". merged ", etc.).
- **The QA trigger was iterated through 7 approaches.** See [`references/workflow-engine-phases.md`](references/workflow-engine-phases.md) for the full approach history. The final working approach (approach 7) is **hybrid git-diff + verifier card**: (1) master HEAD advanced via `git rev-parse`, (2) changed files include code extensions (`.py`, `.js`, etc.) via `git diff --name-only`, (3) a verifier/debugger card completed in the last hour. This is language-independent — it doesn't depend on what the agent wrote in its summary. State tracked via `qa-trigger-state.json` per board. Idempotency key `qa-merge-<sha>`. First run seeds state without creating a card. Approaches 1–6 each failed for a specific reason: git HEAD tracking (PO spec commits), git merge-count (fast-forward merges + first-run seeding), card-based parent-child filter (loop_engine complex chains), regex on summaries (verifiers write "PASS" not "merged"), broader regex patterns (still missed non-standard phrasing), card-based scan with time window (worked but natural-language dependency was fragile).
- **Full script review edge cases (workflow-engine.py, 645 lines).** After 11 livetest rounds, a full review found: (1) `import re` was inside the for-loop body (redundant, already at module level), (2) ESCALATION_CHAIN was missing debugger/qa (blocked cards got immediate HUMAN_REQUIRED), (3) bug routing relied solely on `issue_type == "bug"` without label fallback, (4) the docstring still referenced the old git-based QA trigger. All fixed. Remaining known limitations: the 1-hour lookback window in phase 5 means engine downtime >1h causes permanent QA trigger misses; `completed_at` comparison assumes epoch integers (would silently skip all rows if kanban stored datetimes as strings); and the engine never exits non-zero on top-level exceptions (cron never reports failure).
- **Decomposition hierarchy: slices ARE features, not fragments.** Each tracer-bullet slice (bead) is a complete, independently shippable feature — not a piece of one feature that needs assembly. Slices are progressive enhancements: slice 2 = slice 1 + more capability, slice 3 = slice 2 + robustness. The hierarchy is: epic → slices (beads) → dev/verifier cards (kanban). Tech-lead breaks each slice into dev+verifier execution cards via `kanban_chains` — those are ephemeral kanban cards for one PR's worth of work, not beads. Don't confuse slices with sub-cards.
- **Dispatch is sequential, not parallel.** The workflow engine dispatches one ready bead at a time to the tech-lead. Each tech-lead card receives ONE bead, creates dev+verifier cards, iterates until merge, completes. Then the engine dispatches the next ready bead. In the 3-slice livetest, slices merged ~1 hour apart (05:34, 06:33, 07:31). This means per-merge QA is correct — each merge creates a stable, long-lived state of master (~1 hour) that QA tests independently. The "merge burst" problem (multiple slices merging within minutes) does NOT occur with sequential dispatch. The debounce technique in `qa-trigger-parallel-pipelines.md` was researched under the false assumption of parallel dispatch — it's unnecessary unless the dispatch model changes to parallel.
- **Profile cron jobs.json has a wrapper structure.** The file is `{"jobs": [...], "updated_at": "..."}`, NOT a bare JSON array. Reading it as `json.load()` and iterating directly gives you the dict keys (`"jobs"`, `"updated_at"`), not the job objects. Always extract the `jobs` list: `data.get("jobs", []) if isinstance(data, dict) else data`. Failing to parse correctly makes you report "0 cron jobs" when the profile actually has 3-4 active jobs.
- **SOUL.md refactor requires gap analysis before removal.** When stripping procedures from SOUL.md to make it identity-only, you MUST read each target operational skill in FULL and verify it covers every procedure being removed. A rushed refactor of 6 profiles (committing all rewrites in one code block without reading skills) found 18 gaps after-the-fact via 3-subagent cross-reference review — including a QA live-testing skill that was actively WRONG (routing findings to `developer` as kanban cards instead of beads to `debugger`), a debugger skill missing the merge-gate procedure entirely (saying "never merge" without saying "create a verifier card for merge"), and a `live-testing` skill simultaneously in `mandatory` AND `disabled` (bricking the enforcer pin — the skill couldn't load, the enforcer couldn't enforce it, and the agent was configured to refuse it). The correct sequence is: (1) dispatch 3 subagents to cross-reference each SOUL.md against its operational skill line-by-line, (2) patch every gap found in the skills BEFORE touching SOUL.md, (3) commit skill patches, (4) THEN rewrite SOUL.md to identity-only, (5) dispatch 3 more subagents to review the final state (writing-great-soul line test, coverage, contradictions, enforcer pin correctness). Never batch-remove from SOUL.md before skills are proven complete. The user's exact words when catching the rushed refactor: "damn. do it again. cleanly. only the best result accepted or else my live will end here."
- **Never claim a livetest is COMPLETE without verifying every step ran autonomously.** The most damaging false-claim pattern: reporting a livetest as "COMPLETE" when QA didn't actually fire (because you manually intervened to create the QA card), or when you restarted gateways mid-run (invalidating the test). The user's test: "did the livetest is running now?" and "which livetest? did you run the e2e that complete every step including qa and debugger yet?" — if they have to ask, the claim was premature. Before reporting COMPLETE: (a) verify QA cards were auto-created by the workflow engine (not manually), (b) verify no manual intervention occurred after the trigger card was created, (c) check that the bug→debugger→QA re-test loop (if bugs were found) ran without intervention, (d) verify the QA trigger actually fired — don't assume it worked just because the engine ran. If you intervened, say so explicitly — "the pipeline ran but QA didn't fire autonomously; I manually seeded the state and ran the engine" — don't claim it was clean. The user expects you to run the FULL loop without touching anything, and will deliberately add edge-case traps to specs to ensure the debugger+QA loop fires. When the user says "sure! isn't that I asked you to do?" after you offer to run a clean e2e, it means you cut corners — re-run it properly with zero intervention.
- **The skill-enforcer dead-pin trap.** When a skill appears in BOTH `skill_enforcer.mandatory` AND `skills.disabled` in the same config.yaml, the pin is completely dead. `skill_view()` refuses disabled skills (returns `success: false`), and the enforcer plugin only reformats results where `success` is truthy — so the directive framing never fires. The agent can't load the skill, the enforcer can't enforce it, and the SOUL.md points to a skill the agent is configured to refuse. This happens when copying a profile config from a template (templates disable everything the source doesn't use) and later adding the skill to `mandatory` without removing it from `disabled`. Always diff `mandatory` against `disabled` when setting up enforcer pins.
- **Structured output contracts were tested and REVERTED — lesson captured, implementation shelved.** Approach 8 (`feat/structured-output-contracts`, commit `4bae628`) added `merged_commit_sha` to verifier metadata and structural QA trigger detection. The concept is correct (structural metadata replaces regex parsing) and the livetest proved the verifier stamps structured metadata naturally (`{verdict, acs_verified, findings_count, findings, adr_conformance, dev_tests}`). However: (1) the livetest never produced a merge (tech-lead caught duplicate beads and refused to merge), so the `merged_commit_sha` trigger path was never exercised end-to-end, (2) the user reverted the branch to plan better ("we need to better plan. let test with smaller scale first"). The contracts will be re-implemented as part of the new workflow engine (v1 built, see below), where IO schemas are first-class node declarations in the JSON template rather than skill-text instructions. The design lives in `references/workflow-node-contracts.md`.
- **Design principle: structural signals replace fragile heuristics.** When the engine needs to detect a structural event (merge, verdict, completion), the agent that performed the event should declare it in structured metadata — not describe it in prose. This is the #1 lesson from the QA trigger pain (gaps 11-16, 5 iterations of regex/git/card detection). Design #2 from the 8-doc workflow engine design session (IO schema model, rated 9/10) formalizes this: every node declares an output schema (JSON Schema Draft 2020-12), the engine validates `task_runs.metadata` against it, and downstream triggers are structural, not lexical. This principle applies beyond QA triggers — anywhere the engine inspects agent output to make routing decisions, use a metadata contract instead of natural-language parsing.
- **Duplicate beads cause destructive merges (gap 18).** The PO's `to-tickets` decomposition can create duplicate slices (same title, same description, different bead IDs). Each duplicate spawns a separate tech-lead card with a separate branch, and the branches diverge from different baselines — merging the second branch destroys the first's hardened work via conflict. The tech-lead's escalation review (iteration-3 circuit breaker) is the safety net: "CORRECTED VERDICT: DO NOT MERGE — bead is redundant, branch would destroy master." The root fix is PO-side: deduplicate beads by title+description before creating them.
- **Workflow engine v1 built and tested (`feat/workflow-engine` branch).** The new declarative workflow engine is built and verified (51/51 structural checks + 30/30 integration tests). Architecture: `model.py` (Workflow/Node/Trigger dataclasses + template resolution + condition evaluation + mermaid rendering), `store.py` (TemplateStore — loads JSON from `templates/`), `kanban_adapter.py` (thin wrapper: `create_card`, `get_card`, `get_card_metadata`, `find_recent_completions`, `validate_output`), `runtime.py` (Engine tick loop + StateDB with `workflow_instances` + `node_states` + `trigger_watermark` tables), `main.py` (CLI: tick/loop/list/render/start/templates). First template: `qa-loop.json` (QA re-test on verifier PASS+merge). Proven: manual workflow start creates instance → dispatches node → creates kanban card with resolved `${trigger.*}` variables → idempotency key deduplicates. State DB is a rebuildable cache (kanban is ground truth). The old 645-line cron and the new engine will coexist during incremental migration — each cron phase gets replaced by a JSON template one at a time, livetested independently. Package directory MUST use underscore (`workflow_engine/`), not hyphen (`workflow-engine/`) — Python can't import hyphenated package names.

- **Use JSON for machine-generated configs, not YAML.** Workflow templates are read by the engine and potentially generated by agents. JSON wins because: JSON Schema validation is native, no indentation/tabs-vs-spaces ambiguity, no implicit type coercion (YAML parses `yes`/`no`/`on`/`off` as booleans), strict parsing fails loud. YAML's only advantages (comments + multi-line strings) don't matter when the file is validated by schema and generated programmatically. The user caught this default: "why chose yaml over json?" — I had defaulted to YAML out of habit without thinking about the use case.

- **Test new infrastructure components with fakes BEFORE livetesting.** The user's correction (exact quote): *"we need to better plan. let test with smaller scale first"* and *"write tests that fake every parts of workflow to see how this engine work."* Livetests are slow (hours), expensive (many dispatches), and non-deterministic. For new engine components, write a FakeWorld test suite (fake SQLite boards, monkey-patched KANBAN_HOME, simulated card completions) that runs in milliseconds. Graduate to livetests only after the fake tests prove the engine mechanics are correct. The workflow engine v1 has 30 such tests (15 happy paths + 15 edge cases) — see [`references/workflow-engine-testing-pattern.md`](references/workflow-engine-testing-pattern.md) for the pattern.

- **Engine tick ordering: completions BEFORE pending dispatches.** Critical bug discovered via testing: if the tick loop checks pending nodes before checking completed nodes, a card that completes in this tick doesn't advance its downstream node until the NEXT tick — adding one tick of latency per pipeline hop. Fix: two-phase tick — phase 1 reads completions and updates in-memory NodeState, phase 2 dispatches pending nodes (which now see updated deps). The in-memory update is essential: updating only the DB doesn't help because the same tick's phase 2 reads from the in-memory instance object.

- **Don't expand scope when the user wants focus.** When the user says "ignore this. scope creep rn. we will do other idea first," they're redirecting — stop the current exploration and follow. I had expanded an R&D discussion into 4 product ideas when the user wanted to focus on the workflow engine. The lesson: when a user asks for X, deliver X. If related ideas come up, note them but don't expand the task. Scope expansion is the user's call, not the agent's.

When testing the pipeline end-to-end, the user expects **continuous monitoring with milestone reporting** — not periodic checks with pauses between them. Key lessons from livetest sessions:

- **Monitor continuously.** Use background processes (`notify_on_complete=true`) or tight polling loops. Never stop monitoring and tell the user "I'll report when done" — the user wants real-time milestone updates as each agent picks up, completes, or fails. Background `notify_on_complete` fires ONCE when the process exits — it does NOT notify per-milestone. For per-step reporting, poll actively in foreground loops or set up milestone-tracking background scripts that detect state transitions.
- **Report every milestone.** Each gate the pipeline crosses is a reportable event: PO picks up card, architect design complete, beads created, tech-lead dispatched, dev↔verifier iterations, merge, QA, bug found, debugger converges, QA re-test. If the user asks "did it stop?" you failed to monitor — the pipeline runs for hours and every handoff is a potential silent failure. The user explicitly said "monitor and report me every step it reach too" — this is a hard requirement, not optional.
- **Never pause without reporting.** If you hit a context limit or compaction, say what happened and what state the pipeline is in. The user found a 4-hour gap with no updates because monitoring stopped — that is a failure, not an acceptable pause.
- **Trace each step's evidence.** Don't just see "done" — verify HOW it completed. Did the verifier actually review code? Did the fix actually merge? Did QA actually re-test the running artifact? Did the debugger create follow-up cards or just close the bead?
- **Check for handoff gaps proactively.** The pipeline has many handoffs (debugger→verifier for merge, verifier→QA for re-test, debugger→QA for already-fixed case). Each handoff is a potential silent failure where work sits because nobody created the next card. Verify the full chain completed — "bug closed" means nothing if QA never ran.
- **Run multiple livetests.** Each run finds different bugs. First run: structural bugs (deadlocks, missing gates). Second run: routing bugs (issue_type mismatch). Third run: edge cases (already-fixed bugs, stale QA reports). Keep testing until a full run completes with zero new bugs.
- **Never claim "COMPLETE" without verifying every step ran autonomously.** The most damaging false-claim pattern: reporting a livetest as "COMPLETE" when QA didn't actually fire (because you manually intervened to create the QA card), or when you restarted gateways mid-run (invalidating the test). The user's test: "did the livetest is running now?" and "which livetest? did you run the e2e that complete every step including qa and debugger yet?" — if they have to ask, the claim was premature. Before reporting COMPLETE: (a) verify QA cards were auto-created by the workflow engine (not manually), (b) verify no manual intervention occurred after the trigger card was created, (c) check that the bug→debugger→QA re-test loop (if bugs were found) ran without intervention. If you intervened, say so explicitly — "the pipeline ran but QA didn't fire autonomously; I manually seeded the state and ran the engine" — don't claim it was clean.
- **The `bd link` command doesn't exist — use `bd dep add`.** Trying to link a bug bead to an epic with `bd link <bug> <epic>` fails with "tasks can only block other tasks, not epics." The correct command is `bd dep add <bug-id> <epic-id>`. This matters for QA's `bd link` instruction when filing bug beads — it should use `bd dep add` or the equivalent `bd link` syntax that works with the installed version. Verify the command works before instructing agents to use it.
- **Add deliberate edge-case traps to specs to exercise the debugger loop.** When livetesting the full pipeline (including QA → debugger → fix → QA re-test), the test project may not produce bugs that survive dev↔verifier review. To guarantee the debugger loop fires, inject subtle edge cases into the spec that are hard to catch in code review but obvious in black-box QA. Examples that worked: whitespace-padded numbers (" 42 " must be string not int), comma-in-quoted-fields ("1,000"), inf/nan as strings, leading zeros ("007" must be string). These survive the verifier (who reads code, not data) but get caught by QA (who runs the tool with real input). The trap exercises the full loop: QA finds bug → files bead → debugger routes → fix → merge → QA re-test.

## R&D comes before design — universally

When designing or extending the development pipeline, R&D/exploration goes BETWEEN spec and architect, not after. Research confirms this universally: Google's mandatory "Alternatives considered" in design docs, Amazon's Working Backwards (problem validation before engineering), Ousterhout's "Design It Twice", Toyota's set-based design, YC's build-measure-learn. The current Hermes pipeline (grill → spec → architect → build) skips exploration — the architect designs ONE approach without questioning whether it's the right approach. The fix is an exploration phase between spec and architect (problem defined → explore 2-4 approaches → pick winner → architect designs production informed by the dossier). This is a skill (PO-owned, like `architect-gate`), not a new profile. Karpathy's `autoresearch` pattern (autonomous experiment loop: modify → run → measure → keep/discard) maps to the spike-prototype mode of this phase — but only works when you have a measurable success metric. Most ideas need discovery (problem framing) before any technical exploration.
