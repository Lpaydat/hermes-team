Investigate a question against **primary sources** — official docs, source code, specs, first-party APIs, authoritative books/papers — not a secondary write-up of them. Follow every load-bearing claim back to the source that owns it. The goal is a findings file a reviewer (or future you) can trust without re-reading the sources: **short verbatim quotes + source URLs inline**.

## When to reach this skill

Reach it instead of answering from your own priors whenever the answer is **load-bearing** — it will justify a design decision, a build, a vendor choice, or a claim about how the world works — *and* a primary source exists. If it's a quick factual lookup your training covers confidently, just answer.

## Steps

1. **Name the primary sources before you fetch.** List which sources would be authoritative for this question (official docs for a tool's behaviour; the vendor's own blog for their architecture; a foundational book/paper for an established practice; the RFC/spec for a protocol). If you can't name a candidate primary source, say so and fall back to the best available secondary sources, labelling them as such.

**Check tool/vendor currency as a first-pass filter.** Before committing deep research effort to a tool, library, or vendor, confirm it is still actively maintained. Curl the vendor homepage or GitHub repo and grep for deprecation, sunset, EOL, or archived-status signals. This avoids wasted effort researching something that has been deprecated since your training data — e.g., discovering only mid-research that Lucia was deprecated in March 2025. A 5-second status check before the deep dive saves a full research pass on a dead tool. When comparing N tools, batch the status checks in one curl loop alongside the URL probes (§9).

2. **Gather in parallel, serialize on dependency.** Open independent sources concurrently. Only serialize when one source's URL/path depends on another's result (e.g. a chapter link found inside a book's TOC). For web sources, use the browser tools — their mechanics are in [`references/web-research-tactics.md`](references/web-research-tactics.md) and they materially speed up a pass (truncated snapshots, navigating dense doc pages, paywalled/moved sources). When you have many candidate URLs to screen (restructured docs, mirror triage), batch-probe them with [`scripts/probe-urls.sh`](scripts/probe-urls.sh) (tactics §9) before committing to full fetches. Platform-specific extraction patterns: **YouTube talks/podcasts** — pull title, full description (chapters, slide links, author annotations) via curl + embedded JSON parse (tactics §15); **GitHub repos** — fetch READMEs/configs/prompt files via `raw.githubusercontent.com`, discover an author's repos by topic via `api.github.com/users/<user>/repos` (tactics §16). **Comparing JS/TS frontend libraries/component frameworks** — see [`references/js-library-research.md`](references/js-library-research.md) for the two-layer (headless→styled) architecture model, the "maintainer moved to successor" liveness signal, the proven GitHub API batch sequence for N-library comparison (§5), the **npm registry + downloads API as a rate-limit-free data layer** when GitHub's 60/hr limit hits (§9 — pivots to npm version/last-modified/downloads data instead of waiting), and the **three-layer output shape** (per-library detail → summary matrix → per-use-case picks) for multi-dimensional comparisons of 10+ libraries (§10). **Researching an open-core product** (Community vs Enterprise Edition, licensing, SDK coverage — Neo4j, GitLab, Grafana, Supabase, etc.) — see [`references/open-core-product-research.md`](references/open-core-product-research.md) for the official docs feature-table extraction, repo-structure analysis for the CE/EE boundary, license triangulation (GPLv3 vs AGPL SaaS filter), cross-registry SDK mapping, **and acquisition history / adoption-risk assessment** (§8: ownership tracking via GitHub Discussions, maintenance-liveness verification via CHANGELOG, "is it safe for new projects" verdict structure). **Comparing auth libraries / SDK-based middleware across backend languages** (does tool X work with language Y? SDK coverage, session-token architecture, sidecar requirements) — see [`references/auth-library-architecture.md`](references/auth-library-architecture.md) for the three architecture coupling types (embedded SDK / standalone protocol server / Core+SDK) that determine language compatibility, the compatibility matrix template, and the session findings for Better Auth, Logto, and SuperTokens. **Researching/comparing backend ecosystem standard tools across Rust/Python/Go** (scoring and ranking the canonical packages per category: serialization, async runtime, HTTP client, DB/ORM, etc.) — see [`references/backend-ecosystem-comparison.md`](references/backend-ecosystem-comparison.md) for the scored-table output shape, the registry-data-as-backbone methodology, canonical-vs-alternative classification rules, backend interdependency tracking (runtime lock-in, sync/async mismatch, ecosystem shifts like Go 1.22 ServeMux), and the 1–10 scoring rubric. **Researching/comparing animation or media player libraries** (anime.js, GSAP, Motion/Framer Motion, Auto-Animate; Video.js, Plyr, Vidstack, hls.js, shaka-player, Media Chrome, React Player) — see [`references/animation-media-library-comparison.md`](references/animation-media-library-comparison.md) for verified scored tables (Aug 2026), the engine-vs-UI-vs-all-in-one media library architecture model, the Framer Motion→Motion and Plyr→Vidstack succession facts, GSAP's free-under-Webflow status, and the tech-preferences.json output shape with its validation pattern. **Researching/comparing the TypeScript/JavaScript backend ecosystem** (frameworks, validation libs, realtime, email, file upload for Node/Bun/Deno/Cloudflare Workers) — see [`references/js-backend-ecosystem-comparison.md`](references/js-backend-ecosystem-comparison.md) for the npm registry commands, the edge/Workers runtime-compatibility dimension (the constraining axis that Rust/Python/Go don't have), the bundle-size-decides-on-edge pattern (Zod vs Valibot), the validation↔ORM coupling unique to TS, and verified scored tables for validation/frameworks/realtime/email/ORM (2026-08).

3. **Quote the decisive facts, cite the source.** For each claim that drives the conclusion, capture a short verbatim quote + the source URL inline in the findings file. Quotes are what make the analysis defensible. Reserve full-paragraph quotes for the 2-4 most decisive claims; paraphrase + cite the rest.

4. **Compare and synthesize, don't just transcribe.** The deliverable is a comparison/recommendation, not a link dump. Lay out the approaches, their tradeoffs, who actually uses each, and a decision matrix. Mark any claim you couldn't trace to a primary source as such rather than papering over it.

5. **Save where the repo keeps such notes; say where.** Match the existing convention — repo has `docs/adr/` for decisions, top-level `*-analysis.md` / `*-research.md` for research writeups → put research at the top level, not in `docs/adr/`. If there's no convention, put it somewhere sensible and tell the user the path.

## Source-ranking fallback ladder

When the ideal primary source is unavailable, drop one rung — **don't** silently substitute a secondary blog for a primary source:

1. **First-party primary** — official docs, spec/RFC, the org's own engineering blog, the book/paper itself.
2. **Official open mirror** — same authors/org hosting the same content openly (e.g. a paywalled ACM paper mirrored on `research.google/pubs`; a book's free CC-licensed HTML edition on the publisher's imprint site). Verify it's first-party before citing as primary.
3. **Authoritative secondary** — a respected practitioner/community source that itself cites primaries (e.g. trunkbaseddevelopment.com). Label it as secondary in the findings.

**Copyrighted books with no free full text** break the ladder's assumption that rung 1 is fetchable. For paywalled books (Ousterhout, Hunt & Thomas, Bryar & Carr) there is no official open mirror and no free edition. Cite the book for authority (title/author/chapter/year), paraphrase from established knowledge when confident (never present a paraphrase as a verbatim quote), corroborate with an open source (author's course page, conference talk, publisher page, Wikipedia), and note the access gap in the findings. See [`references/web-research-tactics.md`](references/web-research-tactics.md) §11.

## Completion criterion

Every decisive claim in the findings file carries a short verbatim quote (or an explicit "no primary source found") and a source URL. A reviewer could spot-check any conclusion against its cited source in one click.
