# Workflow Engine Development

Build declarative workflow engines that orchestrate multi-agent pipelines through a kanban board. The engine reads JSON workflow templates, creates kanban cards for nodes, detects card completions as triggers, and advances the pipeline by resolving variables and dispatching downstream nodes.

## When to load

- Building or extending a workflow engine that replaces cron-based orchestration
- Designing JSON workflow templates with nodes, edges, and conditions
- Testing engine code that integrates with Hermes kanban or beads
- Debugging tick-loop ordering, trigger dedup, or state persistence issues

## Core architecture

A workflow engine is a thin scheduler (~300-500 lines) with these components:

1. **Model** (`model.py`) — Workflow/Node/Trigger dataclasses + template resolution (`${variable}` substitution) + condition evaluation (`${var} == 'value'`, `${var} exists`)
2. **Store** (`store.py`) — TemplateStore loads JSON templates from disk
3. **Kanban adapter** (`kanban_adapter.py`) — thin wrapper over `hermes kanban` CLI + direct SQLite reads
4. **Runtime** (`runtime.py`) — Engine tick loop: checks triggers, dispatches nodes, reads completions, resolves variables
5. **Main** (`main.py`) — CLI entry point (tick, loop, list, render, start, templates)

**No framework needed.** The kanban DB holds execution state (card status = node status), beads holds plan state, and the engine's own SQLite holds variable bindings (rebuildable cache). Don't reach for langgraph or other state machine libraries — the kanban dependency graph IS the state machine.

## Key design decisions

### JSON over YAML for workflow templates

Workflow templates are **machine-generated and machine-read**. Use JSON:
- JSON Schema validates input/output natively
- Agents create and read these, not humans typing in editors
- Kanban DB already uses JSON for card metadata — no format mismatch
- Strict parsing — malformed templates fail loud instead of silently misbehaving

YAML's only advantage (comments + multi-line strings) doesn't apply when the file is generated by an agent and validated by a schema.

### Tick-loop ordering: completions BEFORE dispatch

**CRITICAL.** The tick loop must check for completed cards BEFORE checking which pending nodes can dispatch. If you check pending nodes first, a card that completed in a previous tick won't have its node marked DONE, so downstream nodes that depend on it won't see the dependency as satisfied — they wait an extra tick.

Correct order:
1. Phase 1: Scan dispatched nodes for completion → update state
2. Phase 2: Scan pending nodes for dispatch eligibility (deps met, condition passes)

### Engine is unaware of dynamic cards

The engine creates one kanban card per workflow node. Profiles create dynamic child cards at runtime (via `kanban_chains`, `loop_engine`, probe fan-out). The engine does NOT track these children. `kanban_complete` on the parent node card is the sole completion signal. A tech-lead node that ran 5 dev+verifier pairs over 3 hours is "done" when the tech-lead calls `kanban_complete`.

### Trigger dedup: card ID keys, not timestamps

Use a `trigger_keys` table that records `trig:<workflow_id>:<card_id>` for every card that triggered a workflow. Timestamp-based watermarks are unreliable — the same card can re-trigger if the lookback window includes it. The card ID key is permanent and unambiguous.

Lookback window: always scan the last 1 hour. This prevents missing cards during engine downtime without the complexity of precise watermark tracking.

## Testing: the FakeWorld pattern

See `references/fakeworld-testing-pattern.md` for the complete testing methodology. Key principles:

- **Monkey-patch `KANBAN_HOME`** to redirect all board operations to a temp directory
- **Fake `create_card`** to write directly to SQLite instead of calling `hermes kanban` CLI
- **Simulate completions** by inserting rows with `status='done'` + metadata JSON
- **Test the tick loop** by calling `engine.tick()` and asserting on returned actions

## Adversarial testing

After happy paths pass, write tests that try to BREAK the engine. The catalog has grown across five rounds (general, graph-pathology, data-corruption, state-lifecycle, concurrency) and found **20 real engine bugs** total.

### Bug-finder test convention (IMPORTANT)

**The adversarial test suite is NOT expected to be all-green.** Tests that find a bug are written to **FAIL with `AssertionError`** — the `BUG:` prefix in the assertion message IS the bug report. A passing run means the engine is hardened; a failing run means the bug is still there. Do NOT "fix" these tests by relaxing the assertion — fix the engine, then the test flips to passing and becomes a regression guard. Each test docstring carries a `DESIRED:` line; the assertion message carries a `BUG:` line. When adding a new batch, verify the expected outcome split (N bug-finders → FAIL, M confirmed-OK → PASS) with an isolated runner before trusting the full suite.

### Dual-nature test maintenance (when the engine is hardened)

When you fix the bugs the adversarial suite found, the suite flips from a bug *report* to a regression *guard*. Each failing test falls into exactly one of two categories — **triage before editing**, because the fix is different for each:

1. **REAL BUG (fix the engine).** The test asserts correct desired behavior; the engine is wrong. Fix the engine code. The test now passes unchanged. Example: `test_adv_state_bad_created_at` expects a `ValueError` for negative `created_at`; the engine now raises it → test passes, no test edit.
2. **OLD-BEHAVIOR ASSERTION (update the test to match NEW correct behavior).** The engine was hardened in a way that changes observable behavior; the test was written against the OLD (buggy) behavior and now encodes the wrong expectation. Example: a concurrency test that used `threading.Barrier` to *force* a double-dispatch race open will get 0 cards once a file lock serializes the ticks (the second tick returns SKIP) — the test must be rewritten to assert the lock serializes, not that the race fires.

**How to tell them apart:** read the test's `DESIRED:` line and assertion message. If the `DESIRED:` outcome is now actually delivered by the engine, it's category 1 (no test edit). If the engine's new behavior *conflicts* with the `DESIRED:` outcome (e.g., the test forces a race the engine now prevents), it's category 2 (update the test's setup + assertion to assert the hardened behavior, preserving the `DESIRED:` docstring intent).

**Never delete a test.** A category-2 test is still a regression guard — it now guards that the lock/serialization stays in place. Rewrite its harness and assertion, keep it in the suite.

Key adversarial categories:
- **Self-triggering loops** — workflow whose node assignee matches the trigger condition
- **State DB deletion** — tables disappear mid-workflow (fixed: `_ensure_schema()`)
- **Trigger dedup** — same card re-triggers across ticks (fixed: `trigger_keys` table)
- **Template injection** — metadata containing `${}` patterns
- **Dead branches** — conditional nodes whose condition never passes
- **Rapid ticks** — calling `tick()` 10 times instantly (idempotency must hold)
- **Ghost dependency** — node depends on a node that doesn't exist
- **Graph topology/pathology** — disconnected components, cycles, impossible conditions, star topology, 50-node fan-out. See `references/graph-pathology-tests.md` for 10 topology tests. **Core weakness: every pathological graph silently deadlocks forever — no cycle detection, no reachability analysis, no liveness check, no staleness timeout.** Assert the deadlock exists (to catch a future fix) but document it as a weakness, not a desired property.
- **Data corruption** — null fields, unicode/null-bytes, huge payloads, condition-parser edge cases. See `references/data-corruption-tests.md` for 20 tests. **Core weaknesses: crashes on explicit JSON `null` fields (the `.get(key, default)` trap) + `str()`-based data corruption for non-string template values.**
- **State & lifecycle** — zombie instances, dangling card references, orphaned rows, card regression, state-DB-vs-board disagreement, read-only DB crashes, unbounded growth. See `references/state-lifecycle-tests.md` for 12 tests that found **10 real bugs** — all now **FIXED** (techniques in `references/engine-hardening-techniques.md`). The core weakness (engine trusts its own state DB as ground truth, never reconciling against the board) is addressed: zombie detection via `completed_at`, deleted-board detection via `board_db_path().exists()`, card-regression checks on DONE nodes, board re-verification before instance completion, stale node-state filtering via `node_ids` snapshot, and negative-`created_at` validation.
- **Concurrency** — races, simultaneous access, partial writes, DB locking. See `references/concurrency-tests.md` for 6 tests that found **6 real bugs** — all now **FIXED** (techniques in `references/engine-hardening-techniques.md`). The core weakness (zero locking, non-atomic read-modify-write) is addressed: `tick()` uses an internal `threading.Lock` (`_tick_lock`) + a cross-process `fcntl` file lock; `update_node_state` is a single-statement COALESCE-merge UPSERT (no read-then-write); trigger dedup is atomic check+record in one connection. **When the engine was hardened, the concurrency tests' assertions were UPDATED** — see the "Dual-nature test maintenance" note below.
- **Trigger system** — the card-completion → workflow-start coupling: discover (`find_recent_completions`), match (`_matches_trigger`), start (`_start_from_trigger`). See `references/trigger-system-tests.md` for 12 tests that found **6 real bugs**. **Core weaknesses: a hardcoded `LIMIT 20` in the adapter SQL silently drops 80% of a trigger storm; an empty `condition: {}` falls through to `return True` (trigger-everything bomb); no board scoping (a card on board B triggers a workflow on board A); flat-only metadata lookup (`metadata.a.b.c` never traverses a nested dict); `WHERE completed_at > ?` makes NULL-timestamp done cards invisible; no `wf:` idempotency-prefix filter so engine-created cards re-trigger their own workflow.** Probe each stage of discover→match→start for both false negatives (matching card missed) and false positives (non-matching card started).
- **Data corruption** — malformed field *content* rather than graph shape: null values where strings are expected, unicode/emoji/null-bytes, 10k-char payloads, condition-parser edge cases (double quotes, trailing garbage, malformed operators), template-injection via data values. See `references/data-corruption-tests.md` for the full catalog of 20 tests. **Core weakness: zero input validation in `from_dict`** — the JSON-null-vs-missing-key trap (`n.get("body_template", "")` returns `None` for an explicit `null`, not `""`), and `resolve_template`'s `str()` on non-string values embeds Python repr instead of JSON. The condition parser (`evaluate_condition`) silently fails on double quotes, ignores trailing garbage (`re.match` not `re.fullmatch`), and returns `False` with no diagnostic for unrecognized expressions.

**Adversarial-test methodology:** read all engine source first, list concrete code-level weaknesses, then write one test per weakness whose docstring states the exact line/statement it targets (`WEAKNESS: ...`). Tests encode current behavior (passing) or catch the bug (failing → regression guard after fix). See `references/adversarial-test-catalog.md` and `references/data-corruption-tests.md` for worked examples.

## Pitfalls

- **Check completions first.** If you dispatch before checking completions, downstream nodes wait an extra tick. This is the #1 tick-loop bug.
- **Don't use timestamp watermarks for trigger dedup.** Cards completed within the lookback window will re-trigger on every tick. Use card ID keys.
- **Don't use `INSERT OR REPLACE` for fake card creation in tests.** Multiple cards created in the same millisecond get the same ID. Use a counter.
- **Handle state DB deletion.** `StateDB.load_active_instances()` crashes if tables don't exist. Add `_ensure_schema()` to every read method.
- **Python package name must use underscores.** A directory named `workflow-engine` can't be imported as `workflow_engine`. Rename the directory, not the import.
- **Don't append test functions after the `if __name__ == "__main__"` runner block.** The runner calls `sys.exit()` at its end, so functions defined after it are never executed → `NameError` when the runner's list references them. Insert new test defs *before* the `# RUN ALL TESTS` header and add them to the `tests = [...]` list. If a concurrent worker edits the same test file, verify with `grep -n 'if __name__\|def run_'` that helpers are defined above the runner before executing.
- **JSON null is not a missing key.** In `from_dict`, `n.get("field", "")` returns `None` when the key exists with value `null`, not the `""` default. Coerce every optional string field with `n.get("field") or ""` so `None`, missing, and empty all map to `""`. An explicit `null` in `body_template`/`profile` otherwise crashes `resolve_template`/`re.sub` or writes a NULL assignee column.
- **Make race windows deterministic with `threading.Barrier`, not bare threads.** Bare `threading.Thread` tests pass ~99% of the time because the scheduler rarely interleaves at the exact vulnerable seam (check-then-act, read-then-write). Place a `Barrier(2)` *at the seam* — between the existence-check and the create, or between the SELECT and the UPDATE — so both threads reach the vulnerable point simultaneously. Always set `barrier.wait(timeout=5)` and `t.join(timeout=10)` so a broken harness fails fast instead of hanging the suite.
- **When sibling agents edit the same test file concurrently, write to a standalone file first.** If `patch` reports the file was modified by a sibling and the anchor is no longer unique, don't thrash against a moving target. Write the tests to `test_<category>_standalone.py` that `import`s `FakeWorld` from `test_engine.py`, run them to confirm they break the engine, *then* append to the shared file once you have a fresh read. This avoids lost-write loops and gets you real results faster.
- **`find_recent_completions` has a hardcoded `LIMIT 20`.** A trigger storm (>20 matching cards completed in the lookback window) silently drops everything past the 20th — the adapter drops them *before* the trigger matcher even sees them. When testing triggers, always include a storm-scale test (100+ matching cards); single-card tests will never surface this. The fix is to paginate or raise/remove the LIMIT and rely on `trigger_keys` dedup to bound work.
- **An empty trigger `condition: {}` matches every completed card.** `_matches_trigger` iterates `condition.items()`; an empty dict skips the loop and falls through to `return True`. A misconfigured template (`"condition": {}` or a missing `condition` key) becomes a trigger-everything bomb across all boards. Reject empty conditions at template load time.
- **`metadata.a.b.c` does a flat lookup, not nested traversal.** `_matches_trigger` does `field = key.split('.', 1)[1]` then `meta.get(field)`. So condition `metadata.a.b.c: "deep"` matches a card whose metadata literally has key `"a.b.c"`, but NOT a card with `{"a":{"b":{"c":"deep"}}}`. If you need nested matching, split the full path and walk the dict.
- **Atomic UPSERT with COALESCE: the NOT NULL trap.** To merge a partial update (caller omits `card_id` or `output`) without a read-then-write, use `INSERT ... ON CONFLICT DO UPDATE SET card_id=COALESCE(?, node_states.card_id), output=CASE WHEN ?=1 THEN ? ELSE node_states.output END`. But the `VALUES` clause must supply a **non-NULL** placeholder for any NOT NULL column, or the INSERT half fails before the conflict is ever reached: `output TEXT NOT NULL DEFAULT '{}'` rejects an explicit NULL even though ON CONFLICT would have merged it. Fix: pass a non-NULL default into VALUES (`output_json if output_json is not None else "{}"`), then let the ON CONFLICT clause apply COALESCE/CASE so the existing value is preserved for omitted fields. The COALESCE merge on a *single* SQL statement is what makes concurrent field-level updates safe — two threads each setting a different field both survive.
- **Stale-node filtering needs a snapshot, not the live template.** `load_active_instances` can't see the template store, so it can't filter node states against the current template directly. Solution: store a `node_ids` JSON array (the valid node IDs) on the instance *at creation time*, and filter node states loaded from the DB against that snapshot during load. This catches nodes removed from the template after the instance started. The in-memory `_check_instance` then does a second filter against the live template for defense in depth.
- **`completed_at` is the zombie-detector column.** Store `completed_at` (epoch seconds) on the instance row when `complete_instance` runs. In `_check_instance`, check `inst.completed_at is not None` *first* — if an instance was previously completed and somehow reactivated (manual SQL `UPDATE ... status='active'`), skip it and re-mark complete. This prevents phantom work from a "finished" instance.
